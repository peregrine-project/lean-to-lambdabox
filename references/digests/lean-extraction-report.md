## One-paragraph summary

The report builds and benchmarks a **from-scratch bridge from Lean 4's elaborated term language (`Expr`) directly to λ□**, targeting Rocq's verified extraction pipeline (Forster/Sozeau/Tabareau 2024, "Verified Extraction from Coq to OCaml") via the `lbox` tool (an ancestor of `peregrine`) and the Malfunction/OCaml backend, in order to empirically compare this "extraction via OCaml" path against Lean 4's own native compiler (Expr -> LCNF -> IR -> C, with Perceus-style reference counting). It describes the erasure algorithm (Letouzey's method adapted to Lean, with a dedicated `EraseM` monad, eta-expansion for underapplied constructors/`casesOn`, `@[macro_inline]`/matcher/`@[csimp]` preprocessing), special-cased efficient arithmetic (Nat/Int via Zarith, `@[extern]` axioms), three implementations of persistent functional arrays (Sek, Baker's-trick difference lists, an unsafe Dynarray-based one), and a constructor pruning + unboxing optimization split between the erasure step and a patched `lbox`. It benchmarks ~19 program variants (10 distinct programs) adapted from the "Counting Immutable Beans" (Ullrich & de Moura 2021) suite plus a few toy programs, across 10 pipeline configurations, using hyperfine. Headline result: Lean's native compiler is on average ~2.5x faster (geometric mean) than the OCaml/Malfunction pipeline, with wide per-benchmark variance (Lean loses badly on `unionfind`, a monadic benchmark, by >10x, because inlining hints are not preserved through λ□; the OCaml pipeline sometimes wins, e.g. on `even`, because Lean lacks tail-call optimization for mutual recursion). The report contains **no formal verification of the Lean-to-λ□ erasure**; it is presented purely as an unverified engineering bridge and empirical study, explicitly recommending (as future work) that someone build a *verified* forward simulation, and separately that a translation from λ□ into an intermediate stage of Lean's own compiler (to reuse its reference-counting optimizations for Rocq/Agda-erased code) would be valuable.

## What it establishes

- A working, unverified Lean-`Expr`-to-λ□ erasure implemented as a Lean 4 module (`Erasure`, with `#erase <term> to <path>` command) -> Section 4, p.10-15.
- λ□'s abstract syntax as re-ported into Lean 4 (`LBTerm`/`GlobalDecl`/`Program`), with an extra `.fvar` constructor not in the original MetaRocq definition, used as an internal free-variable representation during locally-nameless erasure -> Listing 2, p.9.
- A characterization of Lean's elaborated `Expr` syntax itself (10 constructors: `lit`, `sort`, `const`, `app`, `proj`, `bvar`, `fvar`, `lam`, `forallE`, `letE`), noting that constructors, pattern matching and recursion are *not* primitive in `Expr` but encoded via `casesOn` eliminators and top-level `const` references -> Listing 1 and surrounding text, Section 3.2, p.7.
- A description of Lean's own native compiler pipeline as points of comparison: elaboration to `Expr` -> `let rec` lifting to top-level mutual blocks -> recursor elaboration (eliminating recursion for the kernel) -> LCNF (A-normal form, with join-point insertion, lambda lifting, dead-argument removal, specialization) -> IR (explicit reference counting, borrowed parameters, destructive-update detection) -> C -> Section 3.2, p.7-8.
- Handling of Lean-specific features not directly expressible in λ□: constructor/`casesOn` under-application via eta-expansion (p.10), `@[macro_inline]` unfolding for strict-evaluation functions like `cond` (p.11), matcher-function inlining and `_unsafe_rec` renaming to bypass recursor elaboration, and `@[csimp]`-directed swap-in of tail-recursive implementations (p.11) -- all done as a Lean-side preprocessing pass before erasure.
- A traversal discipline for binary application spines (`.app (.app a b) c` treated as "a applied to [b, c]") needed to determine constructor/casesOn arity before deciding on eta-expansion vs. direct translation -> Section 4.1, p.10.
- A description of how mutually recursive Lean definitions are grouped and erased together into λ□'s primitive `.fix` construct, and how first encounters of inductive types / top-level constants trigger on-demand addition of declarations to the growing λ□ global environment (memoized inside `EraseM`) -> Section 4.1, p.10-11.
- Efficient arithmetic: Nat/Int represented via OCaml's Zarith (matching Lean's runtime GMP-backed representation), with `.zero`/`.succ` replaced by literal 0 / `fun n => n+1`, `Nat.casesOn` replaced by an `if n == 0 then .. else ..(n-1)` expression, and `@[extern]`-tagged constants (including `Eq.rec`) turned into λ□ axioms resolved by a hand-written OCaml `axioms.ml` module -> Section 4.2, p.12-13.
- An explicit soundness caveat on `@[extern]`: the report notes (footnote 13, p.12) that `@[extern]` is "a source of unsoundness if the external implementation of the function does not match the logical definition" -- i.e. the erasure's correctness (such as it is, informally) is only as good as the hand-written OCaml axioms matching Lean's logical semantics, a trust assumption never discharged.
- Three OCaml implementations of Lean's persistent `Array` API (Sek library / tree-based; Baker's-trick difference-list persistent arrays extended with push/pop; an unsafe non-persistent `Dynarray`-based one used only to measure overhead) -> Section 4.3, p.13-14.
- A constructor-pruning (during erasure, removing computationally-irrelevant constructor arguments) + unboxing (patched into `lbox`'s λ□-to-Malfunction pass, single-constructor single-argument types) optimization pair, explaining why pruning cannot be deferred past erasure (λ□ programs no longer carry argument types) and unboxing cannot be done earlier (Malfunction has no inductive declarations to distinguish "single constructor of many used" from "type truly has one constructor") -> Section 4.4, p.14-15.
- A worked example of why pruning/unboxing must be split this way: `Decidable P` (two constructors `.isTrue`/`.isFalse`, each carrying a propositional argument removed by pruning) needs its `axioms.ml`-side OCaml return type adjusted depending on whether pruning is enabled, illustrating the axiom-boundary fragility introduced by these optimizations -> Section 4.4, p.14.
- A full experimental design: pure `Nat -> Nat` benchmark functions wrapped in minimal Lean/OCaml CLI drivers (to defeat compiler dead-code elimination / constant-folding of pure computations), execution timed with hyperfine on an isolated CPU core, with baseline (`n=0`) subtraction to remove fixed startup overhead -> Section 5.1, p.15-16.
- 10 distinct pipeline configurations tested (reference = Flambda -O2 + inlined axioms + pruning + unboxing + Baker's-trick arrays; plus noflambda, flambda-O0, flambda-O3, noinline, prune-nounbox, noprune-unbox, noprune-nounbox, sekarray, unsafearray) against Lean compiler v4.22.0 (the first release with a fully Lean-self-hosted compiler) -> Section 5.2, p.15-16.
- 10 distinct benchmark programs (19 variants counting sub-variants) adapted from "Counting Immutable Beans" (Ullrich & de Moura 2021) plus original toy programs, covering arithmetic recursion, list folds, tree traversal/construction, symbolic differentiation/constant-folding, red-black-tree maps (4 specialization variants), array quicksort (3 variants), and a monadic union-find structure -> Section 5.3 and Appendix B, p.16, p.25-26.
- An empirical claim (not a theorem): Lean's native compiler outperforms the erasure-via-OCaml/Malfunction pipeline by a geometric-mean factor of ~2.5x across the benchmark suite -> Section 5.4, p.16-18, Table 1 (p.17,26), full data Appendix C.2 (p.27-30).
- A quantified breakdown of *why* the OCaml pipeline is slower: OCaml optimization level (Flambda + `-O2`/`-O3`) is the dominant factor (up to 3.7x geomean regression without it); inlining arithmetic axioms saves ~1.3x geomean; constructor pruning/unboxing gives modest but real gains (largest on `qsort_fin`, where `Fin (2^32)` collapses to an unboxed `Nat`); and the choice of persistent-array implementation matters enormously for array-heavy code (Baker's trick vs. Sek: ~6x; vs. an unsound Dynarray baseline: ~3x faster but silently incorrect under aliasing) -> Section 5.4 and Tables 1-3, p.16-18, p.26-27.
- A causal attribution of the biggest single-benchmark slowdown (`unionfind`, monadic style, >10x) to the fact that λ□/Malfunction carry no inlining-annotation concept, so Lean's `@[inline]`-driven removal of monad-transformer abstraction layers is lost -> Section 5.4, p.18.
- A converse case where the OCaml pipeline *outperforms* Lean's own compiler: the `even`/`odd` mutual-recursion benchmark, because Lean's compiler (as of the tested version) does not perform tail-call optimization across mutually recursive functions -> Section 5.4, footnote 17, p.16.
- An explicit statement that measurement bias (Mytkowicz et al. 2009) was not fully controlled for (single machine, no control for environment-variable-size or link-order effects), though the authors argue the dominant 2.5x effect is large enough to be trustworthy while finer per-configuration effects (a few percent) would need more controlled measurement -> Section 6.2, p.19.
- A recommendation, as future/related work rather than an established result, that the *next* natural step is a λ□-to-(intermediate-stage-of-Lean's-compiler) backend, to let erasure-based frontends (Rocq, Agda) benefit from Lean's reference-counting/Perceus-style optimizations -> Section 6.3 / Summary, p.2, p.20.
- A parallel future-work recommendation to instead evaluate reference-counting-augmented OCaml (Pinto & Leijen's "Exploring Perceus for OCaml" prototype) as a backend that could benefit Rocq's *existing* extraction mechanism as well, independent of any Lean bridge -> Section 6.3, p.20.
- An explicit list of unsupported Lean features that bound the scope of any claim made here: Lean's `IO` monad / side effects, the `Task` API for async/parallel computation, and fixed-width integer types (`UInt32` etc.) -> Section 6.2, p.18-19, and Summary, p.2.

### Hardware and methodology detail (Section 5.1, p.15-16)

- Machine: Intel i5-7200U CPU, 16GB RAM; no swap observed at the tested problem sizes.
- Isolation: hyperfine and the benchmarked process pinned to a CPU core isolated via the Linux `isolcpus` kernel parameter.
- Hyperthreading, Intel Turbo Boost, and CPU idle states were left enabled after preliminary testing showed they did not significantly affect variance.
- CPU frequency held stable at 3100MHz with no observed thermal throttling.
- OCaml version used throughout: 5.3.0. Lean version used: 4.22.0 (first release with the compiler itself self-hosted in Lean rather than C++).
- Per-benchmark parameter `n` was chosen individually so the reference-configuration execution time landed around 0.1s-1s.

### Trust boundary and axioms (as stated or implied in the report)

- Rocq's verified extraction pipeline as reused here: only the Malfunction compiler itself is an unverified/trusted step downstream of erasure (Section 3.3, p.8: "Malfunction's compiler is the only step in the pipeline requiring trust"); erasure-to-λ□ and λ□-to-Malfunction are both stated as formally verified in Rocq.
- The report's own Lean-to-λ□ erasure: entirely unverified/untrusted from a formal standpoint; no claim of a trust boundary narrower than "the whole erasure implementation" is made.
- `@[extern]`/`axioms.ml`: an explicit, named soundness gap -- footnote 13 (p.12) states plainly that mismatched external (OCaml) vs. logical (Lean) definitions for an `@[extern]` function are "a source of unsoundness"; this applies to every hand-written arithmetic, `Eq.rec`, and Array-API axiom the report introduces.
- The unsafe Dynarray-based Array implementation is explicitly flagged (Section 4.3, p.14) as capable of "silently produc[ing] incorrect results or even crash[ing] if the persistence of arrays is relied upon" -- a deliberately introduced, clearly labeled unsoundness used only to measure a performance upper bound, not shipped as a default.
- No axiom in this report (unlike, e.g., Peregrine's CakeML backend's `Axiom trust_coq_kernel` per the Peregrine CLAUDE.md) is stated as a formally tracked Rocq/Lean `axiom` declaration with a name; all of the trust gaps here are informal engineering caveats in prose, not machine-checked trust markers.

## Position in the pipeline

- [kernel theory]: not addressed. No discussion of Lean's or Rocq's kernel typing rules is given beyond an informal, non-formal Appendix-A tutorial (dependent function/pair types, Curry-Howard, subset types) aimed at readers unfamiliar with dependent type theory, not at stating or using a formal typing judgment.
- [kernel verification (type checker correctness)]: not addressed. Neither Lean's C++ kernel nor Rocq's kernel is discussed as a verification target anywhere in the report; both are treated as already-trusted, pre-existing infrastructure.
- [erasure theory]: touched only descriptively, for Rocq's side only. Section 3.3 (p.8-9) restates informally that Rocq's erasure targets λ□ per Letouzey/MetaRocq, citing the formal apparatus (erasure function/relation, `isErasable`) without reproducing it. Section 4 gives an informal (non-formalized, no Coq/Lean proof terms, no inductive relation) account of what erasure from Lean's `Expr` must do operationally; no erasure relation analogous to `erases`/`⇝_E`, no `isErasable` analogue, and no soundness argument (e.g. an analogue of Lemma 4.3's erasability-is-preserved-by-evaluation) is given for the Lean side.
- [erasure verification]: absent, and explicitly acknowledged as absent. The report never states nor attempts a forward-simulation or evaluation-preservation theorem for its own Lean-to-λ□ translation; the closest it comes is an appeal to "arguments supporting validity" in the Summary (p.2) based on benchmark-adaptation fidelity, which is an empirical/engineering argument, not a proof.
- [erasure implementation]: this is the report's central, load-bearing contribution -- a full, shipping (if feature-incomplete: no IO, no Task, no fixed-width ints) Lean-`Expr`-to-λ□ erasure implemented in Lean 4 (Section 4, p.10-15), including its own preprocessing pass (macro-inlining, matcher inlining, csimp substitution) and its own re-implementation of λ□'s abstract syntax (`LBTerm`, Listing 2, p.9). This predates and is architecturally parallel to (not necessarily identical to) the current `lean-to-lambdabox` eraser that Peregrine's verification work targets; a reader auditing the shipping eraser for verification purposes should check how much of this design survives versus was reworked.
- [post-erasure pipeline]: covered via reuse and measurement, not new implementation. The report routes its λ□ output through the existing verified λ□-to-Malfunction translation and unverified `lbox`/OCaml backend (Section 3.3, p.8-9), contributes one small patch to `lbox` itself (the unboxing flag, Section 4.4, p.14), and extensively documents pipeline-level configuration knobs (constructor pruning, unboxing, arithmetic-axiom inlining, choice of Array implementation) together with their measured performance effects (Section 5, Appendix C, p.15-18, p.26-30).
- [extraction implementation]: covered only at the level of consumed external toolchain use (OCaml Flambda, the Malfunction compiler, `ocamlopt`, `axioms.ml` linking) -- these are treated as already-implemented infrastructure the report links against, not as something newly implemented or verified in this work (Section 3.3, 4.2-4.3, p.8-9, p.12-14).

## Appendix A coverage summary (p.20-24; pedagogical, low direct relevance)

Appendix A is a self-contained tutorial for readers unfamiliar with dependent type theory, using a simplified Lean-syntax fragment; it defines no new terms used elsewhere in the report's technical sections and states no theorem. It covers, in order: A.1 simple functional programming (`Nat`, `Bool`, `div2` by pattern matching and recursion, currying); A.2 dependent types (`Type` as a first-class value, dependent function types via `boolvec`/`alltrue`/`double`, dependent pair types via `boollist`, polymorphism via `id`); A.3 logic via Curry-Howard (`True`/`False`, conjunction/disjunction/implication as types, universal/existential quantification, subset types `{x : X // P x}`, proof by induction); A.4 programming with proofs (the `pow` example bundling a computation with a nonzero-result proof, reused verbatim from the main-text Section 2 example on p.5). ## Notes for lean-to-lambdabox verification work specifically

- This report is a *design and performance* precedent, not a verification precedent, for the current `lean-to-lambdabox` project: it demonstrates that a Lean-`Expr`-to-λ□ bridge is buildable and gives a concrete list of the hard cases (constructor/`casesOn` arity, `@[macro_inline]`/matcher/`csimp` preprocessing, `@[extern]` axioms, pruning/unboxing) any correctness argument for the shipping eraser will eventually have to address, but supplies zero lemmas or proof obligations toward that argument.
